## Upstream trust decision (mission item 8)

Observed certificate served by Portainer on the laptop:

- subject: empty; issuer: empty; `Basic Constraints: critical CA:FALSE`
- `Subject Alternative Name: critical DNS:localhost, IP Address:0.0.0.0` (no `192.168.10.217`)
- validity 2026-11-16 16:20:57 GMT to 2031-11-16; generated by Portainer into its `/data` volume

Options considered:

- Pin the certificate (`transport http { tls_trust_pool file <cert> ; tls_server_name localhost }`): the Caddy role template (`caddy/ansible/roles/caddy/templates/Caddyfile.j2`) has no option for it (would need a new per-backend flag), the cert must be copied by hand from the laptop to caddy-70 (cross-repo, out of band), a `tls_server_name` override is needed because the SAN does not match the dialled IP, and any recreation of Portainer's `/data` volume regenerates the cert and turns the site into a silent 502. Not retained.
- Have Portainer serve a certificate from a CA Caddy trusts (`--sslcert/--sslkey` in the laptop role): that is a laptop-bootstrap change outside S3 scope, which would need a CA and a renewal story. Possible follow-up.
- HTTP 9000 upstream: rejected in S1 (credentials and the root-equivalent session token in clear on the Wi-Fi LAN).
- `tls_insecure_skip_verify`: already supported per backend by the template (used by `proxmox`), scoped to the `portainer` block only. The Caddy -> laptop hop stays encrypted (passive sniffing defeated); only an active MITM on the LAN is not detected. Retained.
