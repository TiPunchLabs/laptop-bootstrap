- F1.1 [major] roles/portainer/tasks/main.yml:59 — The pre-exposure check authenticates the currently running instance, not the data volume that the container task will mount. With an existing admin, an empty `portainer_admin_password_hash` (explicitly supported), and `portainer_volume_name` changed to a fresh volume, the old endpoint returns 204 and authorizes recreation directly on the LAN. The replacement then serves setup without an admin until the later status/version/admin tasks stop it. The source filter still permits Caddy during that interval. Expected fix: bootstrap and verify the desired instance on loopback before publishing, or refuse the no-hash path unless the checked container demonstrably retains the desired initialized `/data` volume. - F1.2 [major] roles/portainer/tasks/main.yml:121 — `no_log` depends only on the new hash value. After installation with a hash, clearing that variable is allowed when the existing admin check returns 204. On a subsequent `--check -vvv`, this task has `no_log: false`, while `community.docker.docker_container` returns the existing container facts, including the previous hash in `Args`/`Config.Cmd`. Check mode does not replace the container. The installed collection's `_module_container/module.py` confirms this path: `container_create()` returns `None` in check mode (1112–1148), `present()` retains the old container and assigns `container.raw` to facts (408–555), and `run()` includes those facts in its result (302–319). Diff data can also contain the old command. This violates AC4's no-secret-in-logs/diffs requirement; the current leak tests retain a nonempty hash and miss this transition. Expected fix: make the Portainer container task unconditionally `no_log: true`, and test hash-present → hash-empty with a throwaway hash under verbose check mode, scanning captured output without printing the hash. Update the README's unconditional secrecy claim after verifying this case.
